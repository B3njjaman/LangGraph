Supersteps y reducers

Una ejecución de LangGraph es una sucesión de estados s₀, s₁, s₂, …, uno por superstep. Aquí corren los dos grafos de la lección 1, Euclides y Newton, un superstep a la vez: qué escribe el nodo, cómo el reducer lo junta con el estado y en qué superstep recursion_limit corta la ejecución.

Qué mirar

  • El corte de recursion_limit. Euclides con (1071, 462) usa los supersteps 0 a 3. Con recursion_limit = 4 llega a END. Con 3, la traza muestra s₀ a s₃ y después GraphRecursionError, aunque en s₃ la arista ya eligió END: la ejecución usa cuatro supersteps contando el de START, y el límite es tres.
  • while y do-while. Con b₀ = 0, la arista condicional desde START va directo a END y la ejecución termina en s₀. Con la arista fija, paso corre antes de preguntar y calcula a mod 0: ZeroDivisionError.
  • El reducer. Con operator.add, los cocientes de (1071, 462) se acumulan: [2], [2, 3], [2, 3, 7]. Sin reducer, cada superstep reemplaza la lista y queda [7]. El nodo es el mismo en los dos casos; solo cambia el esquema.
  • Newton y el límite. Con f(x) = x² − 2, x₀ = 1 y ε = 10⁻¹⁰, END llega en el superstep 4: recursion_limit = 4 da error y 5 alcanza. Con x² + 1 no hay raíz real y |f(x)| ≥ 1 siempre, así que la arista nunca elige END. Desde x₀ = 0,5 la ejecución termina en GraphRecursionError, como en la lección. Desde x₀ = 1, en cambio, x₁ = 1 − 2/2 = 0, f′(0) = 0 y el paso siguiente divide por cero: ZeroDivisionError.

Las matemáticas

s_0 = s_\varnothing \oplus e

El superstep 0 es el de START: aplica la entrada e al estado parcial s_\varnothing, que solo tiene el valor inicial de cada clave con reducer (Definición 1.12 y su observación). Como la lista vacía es neutra para la concatenación, aquí s_0 coincide con la entrada.

s_t = s_{t-1} \oplus \varphi(s_{t-1}), \quad t \ge 1

En el superstep t corre paso: lee el estado s_{t-1} completo y devuelve una actualización u = \varphi(s_{t-1}) con las claves que cambia (Definiciones 1.7 y 1.12). En el escenario, u es la primera tarjeta y s_t la segunda.

(s \oplus u)(k) = \begin{cases} r_k\big(s(k), u(k)\big) & k \in \operatorname{dom}(u) \\ s(k) & k \notin \operatorname{dom}(u) \end{cases}

Definición 1.8. Sin reducer, r_k(v, w) = w y el valor nuevo reemplaza al anterior (Propiedad 1.9). Con operator.add, r_k(v, w) = v + w, la concatenación de listas.

\texttt{invoke} = \begin{cases} s_n & n + 1 \le L \\ \text{error} & n + 1 > L \end{cases}

Aquí n es el superstep en que la arista elige END y L es recursion_limit, la cantidad máxima de supersteps contando el de START (Definición 1.15). Si la arista nunca elige END y ningún nodo falla, la ejecución entrega s_0, \dots, s_L y se corta con GraphRecursionError.

b_t = a_{t-1} \bmod b_{t-1} < b_{t-1} \;\Longrightarrow\; n \le b_0

En Euclides, b baja estrictamente en cada superstep en que corre paso: es una variante (Definición 1.16). Por eso END llega a más tardar en el superstep b_0, y recursion_limit \ge b_0 + 1 basta (Proposición 1.17). Newton no tiene variante, y con x^2 + 1 nunca llega a END.

Cómo está construido

La página no llama a LangGraph. Las reglas de arriba están escritas en JavaScript, en logica/grafo.js, y los dos grafos, en logica/supersteps.js. Para comprobar que coinciden con LangGraph, pruebas/generar_casos.py corre los mismos grafos con langgraph 1.2.17 en 480 combinaciones y guarda cada sucesión de estados y cada error. Euclides: 8 pares (a₀, b₀), las dos aristas desde START, las tres variantes de cocientes y 6 valores de recursion_limit. Newton: 2 funciones, 8 valores de x₀, 2 de ε, 3 límites y las dos aristas. La prueba de Node exige, en los 480 casos, la misma sucesión de estados, el mismo tipo de error y el mismo mensaje.

El navegador no carga esos módulos uno por uno, sino paquetes/supersteps.js, un solo archivo armado desde ellos. Así la página funciona también abierta como archivo, sin servidor.

Python y JavaScript usan los mismos números de punto flotante, los dobles de IEEE 754, así que las iteradas de Newton salen idénticas bit a bit. La traza las escribe como Python: 1.0 y no 1.

Corre un solo nodo por superstep, como en la lección. Varios nodos en el mismo superstep llegan en el módulo 4.

El código, paso a paso

En cada paso, arriba va el código de la lección y abajo la parte de la simulación que hace lo mismo.

01

El nodo y la condición

Python · lección 1
def paso(s: EstadoMCD) -> dict:
    """La caja: a, b ← b, a mod b."""
    return {"a": s["b"], "b": s["a"] % s["b"]}


def continuar(s: EstadoMCD) -> str:
    """El rombo: sigue con paso mientras b ≠ 0."""
    return "paso" if s["b"] != 0 else END
JavaScript · logica/supersteps.js
const paso = (s) => {
  const { a, b } = s;
  if (b === 0) throw new ErrorPython("ZeroDivisionError", "integer modulo by zero");
  const u = { a: b, b: a % b };
  if (cocientes !== "ninguna") u.cocientes = [Math.floor(a / b)];
  return u;
};
const continuar = (s) => (s.b !== 0 ? "paso" : END);

El nodo devuelve solo las claves que cambia: una actualización, no un estado. En JavaScript, a % 0 da NaN y no un error, así que la simulación lanza a mano el ZeroDivisionError de Python, con su mismo mensaje.

02

La arista desde START

Python · while
constructor.add_conditional_edges(START, continuar, ["paso", END])
constructor.add_conditional_edges("paso", continuar, ["paso", END])
Python · do-while
constructor.add_edge(START, "paso")  # do … while: paso corre antes de preguntar
constructor.add_conditional_edges("paso", continuar, ["paso", END])
JavaScript · logica/supersteps.js
function aristasDeBucle(continuar, entrada) {
  return {
    [START]: entrada === "while" ? { condicional: continuar } : { fija: "paso" },
    paso: { condicional: continuar },
  };
}

La única diferencia entre los dos grafos es la arista que sale de START. La condicional pregunta antes del primer paso, como un while; la fija corre paso una vez sin preguntar, como un do … while. En el dibujo, las aristas condicionales van punteadas.

03

El reducer

Python · lección 1
class EstadoConCocientes(TypedDict):
    a: int
    b: int
    cocientes: Annotated[list[int], operator.add]
JavaScript · logica/grafo.js
if (def.reducer) {
  nuevo[k] = k in nuevo ? def.reducer(nuevo[k], w) : w;
} else {
  if (escritas.has(k)) throw new ErrorPython("InvalidUpdateError", `la clave ${k} recibió dos valores en un superstep`);
  nuevo[k] = w;
}

Es s \oplus u clave por clave. Una clave con reducer combina el valor anterior con el nuevo; una sin reducer lo reemplaza. Las claves que el nodo no devuelve ni se tocan.

04

El bucle de supersteps y su límite

Python · lección 1
for limite in (4, 5):
    try:
        newton.invoke({"x": 1.0, "n": 0}, {"recursion_limit": limite})
        print(f"recursion_limit = {limite}: llega a END")
    except GraphRecursionError:
        print(f"recursion_limit = {limite}: GraphRecursionError")
JavaScript · logica/grafo.js
for (let k = 0; ; ) {
  if (k >= limite) return { pasos, error: { tipo: "GraphRecursionError", mensaje: mensajeLimite(limite) } };
  const siguientes = pasos[k].siguientes;
  if (siguientes.length === 0) return { pasos, error: null };

El orden de las dos comparaciones importa. Primero se mira el límite y después si queda algo por correr; por eso (1071, 462) con límite 3 termina en error aunque la arista ya eligió END. LangGraph hace lo mismo, y los 480 casos lo confirman.

Por qué importa

El resto del curso corre sobre esta misma máquina. Un agente es un grafo con el ciclo modelo → herramientas → modelo: cada vuelta son supersteps, y recursion_limit es lo que lo detiene si el modelo nunca deja de pedir herramientas.

La lista de mensajes de la lección 2 es una clave con reducer, add_messages, y se usa como cocientes con operator.add: cada nodo devuelve solo los mensajes nuevos y el reducer los junta con los anteriores. Y los checkpoints de la lección 5 guardan un s_t por superstep, los mismos estados de la traza.
